FAWRUN — MVP Technical Specification
الإصدار: 1.1
الحالة: مسودة معتمدة للتطوير
يبنى على: وثيقة FAWRUN v1.0 + تقرير القرارات النهائي (52 قسم) + مراجعة الأخطاء
________________________________________
1. نظرة عامة
FAWRUN منصة شراء حاجيات بالنيابة عن العميل وتوصيلها. المندوب يشتري، يوصّل، يستلم الدفع نقداً. FAWRUN تأخذ 25% من رسم الخدمة.
نطاق الـ MVP بدقة: شراء حاجيات من متجر واحد أو أكثر + التوصيل. لا كتالوج، لا دفع إلكتروني، لا تكامل مع متاجر. المتاجر تُكتب يدوياً من العميل كنص حر — لا يوجد قائمة متاجر مسبقة.
________________________________________
2. البنية المعمارية
•	نمط البنية: Modular Monolith داخل Monorepo
•	الفصل: Backend / Frontend منفصلين تماماً
•	التواصل: REST API (/api/v1) + WebSocket (Socket.IO)
•	مصدر الحقيقة: الخادم دائماً وأبداً
لماذا Modular Monolith وليس Microservices؟
في هذه المرحلة Microservices تعقيد غير مبرر. Modular Monolith يعطيك فصلاً منطقياً نظيفاً داخل تطبيق واحد قابل للتحويل لاحقاً إلى Microservices إذا نما الحجم.

4. Stack التقني النهائي
الطبقة	التقنية	السبب
Backend Framework	NestJS + TypeScript	بنية Modules/Services/Controllers، WebSocket مدمج
قاعدة البيانات	PostgreSQL	علاقات معقدة، transactions، Append-only Ledger
ORM	Prisma	Type-safety كاملة، migrations نظيفة
Realtime	Socket.IO (عبر @nestjs/websockets)	WebSocket حقيقي بدل Polling
Validation	Zod	مشترك بين Backend والـ Frontends
Password Hashing	bcrypt (12 rounds)	معيار صناعي
Auth	JWT (Access Token قصير + Refresh Token دائم)	تجديد تلقائي صامت — المستخدم لا يُطرد أبداً مع إمكانية الإلغاء الفوري
Admin Dashboard	Next.js 14 (App Router)	ويب فقط
Runner Interface	React 18 + Vite + PWA	أسرع بالتطوير، يفتح من المتصفح
Customer App	Kotlin (Native Android)	تجربة احترافية حقيقية
الخرائط	OpenStreetMap + Leaflet	مجاني بالكامل، بدون بطاقة ائتمان، بدون حدود استخدام
تحديد الموقع	Browser Geolocation API (PWA) + Android Location API	مدمج في المنصة، مجاني
File Storage	Cloudflare R2	مجاني حتى 10GB، متوافق مع S3 API
الاستضافة - Backend	Railway	Node.js دائم + PostgreSQL مدمج + WebSocket
الاستضافة - Admin + Runner PWA	Vercel	Next.js وReact بدون تعقيد
Error Tracking	Sentry (Free Tier)	مراقبة الأخطاء في الإنتاج
Package Manager	pnpm + Turborepo	سرعة + إدارة Monorepo
ملاحظة الخرائط: OpenStreetMap + Leaflet يوفران عرض الخريطة واختيار الموقع بالسحب والإفلات. تحديد الموقع التلقائي عبر GPS يعمل عبر Browser Geolocation API في PWA وAndroid Location API في التطبيق — كلاهما مجاني ومدمج.

// ─────────────────────────────────────────
// ENUMS
// ─────────────────────────────────────────

enum UserRole {
  CUSTOMER
  RUNNER
  ADMIN
}

enum UserStatus {
  PENDING_VERIFICATION  // بانتظار تأكيد WhatsApp
  VERIFIED              // موثق وفعال
  REJECTED              // مرفوض من الإدارة
  SUSPENDED             // موقوف مؤقتاً
}

enum RunnerStatus {
  AVAILABLE             // مستعد لاستقبال طلبات
  ON_MISSION            // لديه طلب نشط
  UNAVAILABLE           // غير متاح
}

enum OrderStatus {
  DRAFT                       // قيد الإنشاء من العميل
  PENDING_REVIEW              // أُرسل، بانتظار مراجعة الإدارة
  UNDER_REVIEW                // الإدارة تراجعه الآن
  AWAITING_RUNNER             // معتمد، يبحث عن مندوب
  AWAITING_PREFERRED_RUNNER   // العميل ينتظر مندوبه المفضل
  ASSIGNED                    // مندوب معين، لم يبدأ بعد
  IN_PROGRESS                 // بدأ التنفيذ (مرحلة الشراء)
  OUT_FOR_DELIVERY            // انتهى الشراء، في الطريق للتوصيل
  DELIVERED                   // تم التسليم
  CANCELLED                   // ملغى
}

enum OrderStoreStatus {
  PENDING    // لم يزر المتجر بعد
  PURCHASED  // تم الشراء (runner ضغط "تم الشراء")
  SKIPPED    // لم يتم الشراء (متجر مغلق أو مادة غير متوفرة)
}

enum LedgerEntryType {
  ORDER_FEE_TOTAL     // إجمالي رسم الخدمة المحصّل
  RUNNER_SHARE        // حصة المندوب (75%)
  PLATFORM_SHARE      // حصة FAWRUN (25%)
  SETTLEMENT_PAID     // المندوب سدّد حصة FAWRUN
  ADMIN_ADJUSTMENT    // تعديل يدوي من الإدارة
}

enum SettlementStatus {
  PENDING   // لم تُغلق بعد
  SETTLED   // مغلقة ومسواة
}

model User {
  id           String     @id @default(cuid())
  whatsapp     String     @unique  // رقم WhatsApp إلزامي
  altPhone     String?             // رقم اتصال اختياري
  passwordHash String
  name         String
  role         UserRole
  status       UserStatus @default(PENDING_VERIFICATION)
  isDeleted    Boolean    @default(false)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt

  customer      Customer?
  runner        Runner?
  admin         Admin?
  refreshTokens RefreshToken[]
  auditLogs     AuditLog[]

  // الطلبات التي ألغاها هذا المستخدم
  cancelledOrders Order[] @relation("CancelledByUser")

  @@index([whatsapp])
  @@index([role, status])
}

// ─────────────────────────────────────────
// ORDER
// ─────────────────────────────────────────

model Order {
  id          String      @id @default(cuid())
  seqNumber   Int         @unique @default(autoincrement())
  // رقم الطلب المولَّد: FW + seqNumber مُعبَّأ بأصفار حتى 6 خانات
  // مثال: seqNumber=1 → orderNumber="FW-000001"
  // يُولَّد في الكود مباشرة بعد إنشاء السجل باستخدام seqNumber
  // لا يُولَّد قبل الحفظ لضمان التفرد في حالات التزامن
  orderNumber String      @unique

  customerId  String
  customer    Customer    @relation(fields: [customerId], references: [id])

  runnerId    String?
  runner      Runner?     @relation(fields: [runnerId], references: [id])

  status      OrderStatus @default(DRAFT)

  // Snapshot عنوان التسليم (ثابت لا يتأثر بتعديلات العميل اللاحقة)
  deliveryLat  Float
  deliveryLng  Float
  deliveryDesc String

  // التسعير (بالليرة السورية، كأعداد صحيحة)
  isPeripheral        Boolean @default(false)
  baseFee             Int     @default(60)
  peripheralFee       Int     @default(0)
  extraStoresFee      Int     @default(0)
  totalFee            Int     @default(60)

  // المندوب المفضل — ربط رسمي بجدول Runner
  preferredRunnerId   String?
  preferredRunner     Runner? @relation("PreferredRunner", fields: [preferredRunnerId], references: [id])
  waitForPreferred    Boolean @default(false)

  notes             String?
  cancelReason      String?

  // من ألغى الطلب — ربط رسمي بجدول User
  cancelledByUserId String?
  cancelledByUser   User?   @relation("CancelledByUser", fields: [cancelledByUserId], references: [id])

  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
  reviewedAt   DateTime?
  assignedAt   DateTime?
  startedAt    DateTime?
  deliveredAt  DateTime?
  cancelledAt  DateTime?

  items          OrderItem[]
  orderStores    OrderStore[]
  ratings        Rating[]
  auditLogs      AuditLog[]
  ledgerEntries  LedgerEntry[]
  settlementItem SettlementItem?

  @@index([customerId, status])
  @@index([runnerId, status])
  @@index([status, createdAt])
}

// ─────────────────────────────────────────

model OrderItem {
  id       String @id @default(cuid())
  orderId  String
  order    Order  @relation(fields: [orderId], references: [id])

  itemName String  // اسم المادة (نص حر)
  quantity String  // الكمية أو الوصف (نص حر: "2 كغ"، "3 حبات"...)

  // مصدر المتجر — نص حر يكتبه العميل أو المندوب
  // إذا كان anyStore=true فالمندوب يختار المتجر المناسب
  customStoreName  String?  // اسم المتجر الذي كتبه العميل يدوياً
  anyStore         Boolean  @default(true)

  // يُربط بـ OrderStore عند تعيين المندوب له
  orderStoreId String?
  orderStore   OrderStore? @relation(fields: [orderStoreId], references: [id])

  isCancelled  Boolean  @default(false)
  cancelNote   String?
  createdAt    DateTime @default(now())

  @@index([orderId])
}

model OrderStore {

6. State Machines
6.1 Order State Machine
DRAFT
  └─[العميل يرسل الطلب]──────────────────────→ PENDING_REVIEW
                                                      │
                                   ┌──────────────────┤
                                   ↓                  ↓
                             [العميل يلغي]    [Admin يفتح للمراجعة]
                             CANCELLED              UNDER_REVIEW
                                                      │
                          ┌───────────────────────────┼────────────────────┐
                          ↓                           ↓                    ↓
                   [Admin يرفض]         [Admin يعتمد +        [Admin يعتمد +
                   CANCELLED             أي مندوب]             مندوب مفضل غير متاح]
                                      AWAITING_RUNNER      AWAITING_PREFERRED_RUNNER
                                             │                       │
                                  [Admin يعين]          [يتوفر / العميل يغير رأيه]
                                      ↓                       ↓
                                   ASSIGNED ←─────────────────┘
                                      │
                          ┌───────────┤
                          ↓           ↓
                   [العميل يلغي]  [Runner يضغط "بدأت"]
                   CANCELLED         IN_PROGRESS
                                      │
                          ┌───────────┤
                          ↓           ↓
                   [Admin يلغي]   [Runner يضغط "انتقل للتوصيل"]
                   CANCELLED       OUT_FOR_DELIVERY
                                      │
                          ┌───────────┤
                          ↓           ↓
                   [Admin يلغي]   [Runner يضغط "تم التسليم"]
                   CANCELLED          DELIVERED ✓
قواعد صارمة:
•	العميل يستطيع الإلغاء فقط حتى حالة ASSIGNED
•	بعد IN_PROGRESS الإلغاء عبر الإدارة حصراً
•	DELIVERED نهائية — لا تراجع عنها في التطبيق
•	كل انتقال يُسجَّل في AuditLog مع الجهة والوقت
•	عملية "تم التسليم" إذا أُرسلت مرتين تُنفَّذ مرة واحدة فقط (Idempotent)
6.2 OrderStore State Machine
PENDING
  ├─[Runner يضغط "تم الشراء"]──→ PURCHASED ✓
  └─[Runner يضغط "لم يتم الشراء"]─→ SKIPPED ✓
•	قبل PURCHASED يمكن حذف المتجر إذا أُضيف بالخطأ
•	بعد PURCHASED لا تراجع — أي تصحيح عبر الإدارة
6.3 Runner Status Machine
UNAVAILABLE
  └─[Runner يضغط "متاح"]──→ AVAILABLE
                                │
                    [Admin يعين Runner لطلب]
                                ↓
                           ON_MISSION
                                │
                    [الطلب يصل DELIVERED أو CANCELLED]
                                ↓
                           AVAILABLE (آلياً)

7.1 المصادقة
التسجيل (العميل):
•	يُدخل: الاسم، WhatsApp، كلمة المرور، العنوان
•	النظام ينشئ حساباً بحالة PENDING_VERIFICATION
•	العميل يرسل رسالة من رقمه لـ WhatsApp الإدارة (خارج التطبيق)
•	Admin يتحقق ويضغط "تفعيل الحساب" من لوحة الإدارة
•	الحالة تصبح VERIFIED
•	العميل يستلم إشعاراً (WebSocket) بالتفعيل
إنشاء حساب Runner: الإدارة فقط، من لوحة التحكم
JWT Strategy — تجربة "مسجّل دائماً" مع أمان كامل:
عند تسجيل الدخول الناجح:
  - Access Token  (JWT، صالح ساعتين)
  - Refresh Token (random 64-byte string، بلا انتهاء صلاحية)
  - يُحفظ hash(RefreshToken) في جدول RefreshToken

عند انتهاء Access Token (كل ساعتين — يحدث في الخلفية بصمت):
  - التطبيق يُرسل Refresh Token تلقائياً
  - الخادم يتحقق من DB (موجود + غير ملغى)
  - يُولَّد Access Token جديد
  - المستخدم لا يشعر بشيء — التطبيق يبدو "مسجّل دائماً"

عند تسجيل الخروج اليدوي:
  - يُوضَّع isRevoked = true على Refresh Token

إلغاء طارئ من الإدارة (هاتف مسروق مثلاً):
  - يُلغى كل Refresh Tokens للمستخدم دفعة واحدة
  - في أقصى تقدير ساعتين والجلسة تنتهي وحدها
لماذا ساعتان وليس 30 يوماً؟
الـ Refresh Token هو من يبقي المستخدم مسجلاً للأبد — وهو محمي في قاعدة البيانات ويمكن إلغاؤه فوراً. Access Token القصير يضمن أنه لو سُرق لن يعمل أكثر من ساعتين.

8. منطق التسعير (Pricing Engine)
// packages/shared-constants/src/pricing.ts

export const PRICING = {
  BASE_FEE: 60,           // الرسم الأساسي
  PERIPHERAL_FEE: 40,     // رسم المنطقة الطرفية
  EXTRA_STORE_FEE: 20,    // رسم كل متجر إضافي بعد الأول
  RUNNER_SHARE: 0.75,     // 75% للمندوب
  PLATFORM_SHARE: 0.25,   // 25% لـ FAWRUN
} as const;

export function calculateFee(params: {
  isPeripheral: boolean;
  purchasedStoreCount: number;  // عدد OrderStores بحالة PURCHASED فقط
}): {
  baseFee: number;
  peripheralFee: number;
  extraStoresFee: number;
  totalFee: number;
  runnerShare: number;
  platformShare: number;
} {
  const baseFee = PRICING.BASE_FEE;
  const peripheralFee = params.isPeripheral ? PRICING.PERIPHERAL_FEE : 0;
  const extraStoresFee =
    Math.max(0, params.purchasedStoreCount - 1) * PRICING.EXTRA_STORE_FEE;
  const totalFee = baseFee + peripheralFee + extraStoresFee;

  return {
    baseFee,
    peripheralFee,
    extraStoresFee,
    totalFee,
    runnerShare: Math.floor(totalFee * PRICING.RUNNER_SHARE),
    platformShare: Math.ceil(totalFee * PRICING.PLATFORM_SHARE),
  };
}
متى يُعاد حساب الرسم:
•	عند إنشاء الطلب — تقدير أولي (بدون peripheral)
•	عند اعتماد Admin مع تحديد isPeripheral — الرسم قد يتغير
•	عند كل OrderStore يصبح PURCHASED — إضافة +20 إذا كان متجراً إضافياً
•	عند التسليم — الرسم النهائي مؤكد ومقفل
تنبيه العميل: WebSocket event عند كل تغيير في الرسم

9.0 Error Responses (شكل موحد للخطأ)
كل خطأ يُرجعه الخادم يكون بهذا الشكل:
{
  "statusCode": 400,
  "error": "VALIDATION_ERROR",
  "message": "وصف مختصر للخطأ"
}

أكواد الحالة المستخدمة:
- 400: VALIDATION_ERROR — بيانات الطلب غير صالحة
- 401: UNAUTHORIZED — انتهاء الجلسة أو غياب التوكن
- 403: FORBIDDEN — عدم الصلاحية للعملية
- 404: NOT_FOUND — المورد غير موجود
- 409: CONFLICT — تعارض (مثل إرسال "تم التسليم" مرتين)
- 422: BUSINESS_RULE_VIOLATION — انتهاك قاعدة عمل (مثل إلغاء طلب بعد IN_PROGRESS)
- 500: INTERNAL_SERVER_ERROR — أخطاء الخادم الداخلية

كل endpoint يُرجع قائمة يدعم المعاملات التالية:

- limit: عدد السجلات في الصفحة (الافتراضي 20، الحد الأقصى 100)

الـ Response يتضمن دائماً:
{
  "data": [],
  "meta": {
    "total": 150,

async closeSettlementDay(date: string, adminId: string) {
  // 1. جلب كل الطلبات المكتملة في هذا اليوم لكل مندوب
  // 2. تجميعها حسب المندوب
  // 3. لكل مندوب:
  //    - إنشاء Settlement record
  //    - حساب: totalFees, runnerShare (75%), platformShare (25%)

  //    - إضافة LedgerEntry من نوع RUNNER_SHARE و PLATFORM_SHARE
  // 4. تسجيل AuditLog
  // 5. WebSocket إشعار للإدارة بالإغلاق
  // ⚠️ Idempotent: إذا وُجد Settlement لنفس المندوب ونفس اليوم → تخطّى
}
Cron Job للتذكير:
// يعمل كل يوم في 23:00 توقيت دمشق
@Cron('0 23 * * *', { timeZone: 'Asia/Damascus' })
async settlementReminder() {
  const today = getOperationalDate();
  const hasOpenSettlement = await this.checkPendingOrders(today);
  if (hasOpenSettlement) {
    this.wsGateway.emitToAdmin('settlement:reminder', {
      date: today,
      message: 'لديك تسوية معلقة لم تُغلق بعد',
    });
  }
}

قاعدة operationalDate (اليوم التشغيلي):
- اليوم التشغيلي يُحدَّد بوقت بداية الطلب (createdAt) لا وقت تسليمه
- طلب أُنشئ قبل منتصف الليل بتوقيت دمشق ينتمي لذلك اليوم حتى لو سُلِّم بعد منتصف الليل
- جميع التواريخ تُخزَّن بـ UTC في DB، لكن operationalDate في Settlement تُحسب بتوقيت Damascus (Asia/Damascus)
- مثال: طلب أُنشئ 2025-09-10 23:45 Damascus، سُلِّم 2025-09-11 00:15 → operationalDate = "2025-09-10"

14. Security
1.	Helmet.js — HTTP security headers
2.	Rate Limiting: 
o	/auth/login: 10 محاولات / 15 دقيقة لكل IP
o	/auth/register: 3 محاولات / ساعة لكل IP
o	باقي الـ endpoints: 100 طلب / دقيقة
3.	Input Validation: Zod على كل request body
4.	SQL Injection: محمي بالكامل عبر Prisma
5.	Passwords: bcrypt (12 rounds)
6.	JWT: RS256 (مفتاح خاص/عام) — Access Token صالح ساعتين فقط
7.	R2 URLs: Presigned URLs قصيرة الصلاحية (5 دقائق)
8.	HTTPS إلزامي في الإنتاج
9.	Environment Variables: لا أسرار في الكود مطلقاً
10.	CORS: محدود بـ Origins المعتمدة فقط
11.	Database Connection Pooling: إعداد connection_limit في DATABASE_URL لتحمّل الضغط على Railway

17. قواعد Claude Code
•	الخادم هو مصدر الحقيقة — لا تحسب رسوماً أو تغير حالات على الـ Frontend فقط
•	كل انتقال حالة عبر State Machine — لا تغيّر status مباشرة في الـ service بدون المرور بالـ Machine
•	كل عملية مالية = LedgerEntry — لا توجد عملية مالية بدون سجل في Ledger
•	Transactions للعمليات المركبة — تعيين مندوب + تحديث حالته + AuditLog = transaction واحدة
•	Idempotency — عملية "تم التسليم" إذا أُرسلت مرتين تُنفَّذ مرة واحدة فقط
•	لا حذف للتاريخ — Soft delete فقط. AuditLog و LedgerEntry: لا حذف أبداً
•	orderNumber يُولَّد من seqNumber — دائماً داخل transaction بعد الحفظ مباشرة
•	Refresh Token تلقائي — الـ Frontend يجدد Access Token صامتاً قبل انتهائه بـ 10 دقائق
•	لا متاجر في قاعدة البيانات — أسماء المتاجر نص حر دائماً في OrderStore.storeName
•	shared-types أولاً — أي DTO جديد يُكتب في packages/shared-types ويُستخدم في الخادم والـ Frontends
•	API Versioning محترم — كل endpoint تحت /api/v1/ بدون استثناء
•	Zod على كل input — لا ثقة بأي بيانات واردة مهما كان مصدرها
•	Environment Variables فقط للأسرار — لا مفاتيح في الكود أو في Git

18.2 Architecture — MVVM
النمط المعتمد: MVVM (Model-View-ViewModel)
السبب:
• MVVM يفصل الـ View (Compose Screens) عن الـ ViewModel (المنطق) عن الـ Model (Data Layer).
• مع Jetpack Compose، MVVM يتناسب تماماً مع الـ declarative UI.
• الـ ViewModel يحتفظ بالحالة (UiState) عند تدوير الشاشة أو تغيير الاتصال.
• يُمكّن من اختبار Unit Tests بسهولة (ViewModel + Use Cases).

الهندسة:
┌─────────────┐
│  Compose UI │  ← View (State + Effects)
└──────┬──────┘
       │ State Up + Event Down
┌──────▼──────┐
│  ViewModel  │  ← UiState, Intent, SideEffects
└──────┬──────┘
       │ Flow / StateFlow
┌──────▼──────┐
│ Use Cases   │  ← One Use Case per business rule
└──────┬──────┘
       │
┌──────▼──────┐
│  Repository │  ← Data Source (Remote + Local)
└──────┬──────┘
       │
┌──────▼──────┐
│  Data Layer │  ← Retrofit (Network) + Room (Local)
└─────────────┘

AuthInterceptor (Handles JWT):
```kotlin
class AuthInterceptor(private val tokenManager: TokenManager) : Interceptor {
    @Throws(IOException::class)
    override fun intercept(chain: Interceptor.Chain): Response {
        val original = chain.request()
        val token = tokenManager.getAccessToken()
        val requestBuilder = original.newBuilder()
        token?.let { requestBuilder.header("Authorization", "Bearer $it") }
        return chain.proceed(requestBuilder.build())
    }
}
```

JWT Refresh التلقائي:
الحل: Interceptor مخصص يُ Status 401 ويعيد المحاولة.
```kotlin
class RefreshTokenInterceptor(
    private val tokenManager: TokenManager,
    private val api: FawrunApiService
) : Interceptor {
    @Throws(IOException::class)
    override fun intercept(chain: Interceptor.Chain): Response {
        val response = chain.proceed(chain.request())
        if (response.code == 401) {
            response.close()
            val newToken = runBlocking { tokenManager.refresh() }
            if (newToken != null) {
                val newRequest = chain.request().newBuilder()
                    .header("Authorization", "Bearer $newToken")
                    .build()
                return chain.proceed(newRequest)
            }
        }
        return response
    }
}
```

DataStore (Preferences):
```kotlin
class TokenManager(private val dataStore: DataStore<Preferences>) {
    companion object {
        val ACCESS_TOKEN = preferencesKey<String>("access_token")
        val REFRESH_TOKEN = preferencesKey<String>("refresh_token")
        val USER_ID = preferencesKey<String>("user_id")
        val USER_ROLE = preferencesKey<String>("user_role")
    }

    suspend fun saveTokens(accessToken: String, refreshToken: String) {
        dataStore.edit { prefs ->
            prefs[ACCESS_TOKEN] = accessToken
            prefs[REFRESH_TOKEN] = refreshToken
        }
    }

    fun getAccessToken(): String? = runBlocking { // or coroutine
        dataStore.data.first()[ACCESS_TOKEN]
    }

    suspend fun clearTokens() {
        dataStore.edit { it.clear() }
    }
}
```

Sync Strategy:
• Orders sync: when network available, refresh from server.
• Offline queue: if network fails, store in Room, retry with WorkManager.
• Data retention: 7 days offline cache.
